# LLVM metadata design

The runtime uses the public C++ MC interfaces `MCDisassembler::getInstruction`, `MCInstPrinter::printInst`, `MCInstrInfo`, `MCRegisterInfo`, and `MCInstrAnalysis`. It calls AArch64 target-info and disassembler initialization, plus a package-specific MC initializer registering only assembly info, instruction info, register info, subtarget info, instruction analysis, and the standard printer for the fixed little-endian AArch64 target. It does not call `LLVMInitializeAArch64TargetMC()`. LLVM's C disassembler API only exposes text/length; it cannot supply MC operands, opcode descriptors, feature expressions, or all three decode statuses.

The inspection and implementation are pinned to LLVM commit `2078da43e25a4623cab2d0d60decddf709aaea28` (21.1.8):

- [Target.td](https://github.com/llvm/llvm-project/blob/llvmorg-21.1.8/llvm/include/llvm/Target/Target.td): `Instruction.Predicates`, `AssemblerMatcherPredicate`, and `AssemblerCondDag`.
- [AArch64InstrInfo.td](https://github.com/llvm/llvm-project/blob/llvmorg-21.1.8/llvm/lib/Target/AArch64/AArch64InstrInfo.td): real Boolean feature predicates, including alternatives such as SVE or SME, and the permissive `FeatureAll` bypass.
- [AArch64Features.td](https://github.com/llvm/llvm-project/blob/llvmorg-21.1.8/llvm/lib/Target/AArch64/AArch64Features.td): `SubtargetFeature.Implies`, extension descriptions, and `Extension.ArchFeatureName` with authoritative Arm labels.
- [JSONBackend.cpp](https://github.com/llvm/llvm-project/blob/llvmorg-21.1.8/llvm/lib/TableGen/JSONBackend.cpp): `llvm-tblgen --dump-json`, providing fully resolved records after TableGen multiclass/inheritance expansion.
- [AArch64MCTargetDesc.cpp](https://github.com/llvm/llvm-project/blob/llvmorg-21.1.8/llvm/lib/Target/AArch64/MCTargetDesc/AArch64MCTargetDesc.cpp): branch target analysis.
- [AArch64Disassembler.cpp](https://github.com/llvm/llvm-project/blob/llvmorg-21.1.8/llvm/lib/Target/AArch64/Disassembler/AArch64Disassembler.cpp): decode statuses, fallback tables, and operand-specific checks.

`MCInstrDesc` has no public API returning the architectural Boolean requirement tree. LLVM's generated feature verifier computes sets of *predicate* bits, not a minimal set of Arm architectural features. Flattening those predicates to a feature name would lose alternatives. Rather than link TableGen into WASM or use code-generation classes at runtime, a build-time Python extractor consumes the supported JSON dump of resolved records. The resulting schema adapter is explicitly version-coupled to LLVM internals; upgrades require reviewing predicate shapes and tests. Unknown DAG operators or feature references fail generation rather than silently inventing requirements.

For each real AArch64 `Instruction`, the generator collects predicates with `AssemblerMatcherPredicate=1`. All such predicates must hold. Their `AssemblerCondDag` trees are translated without flattening OR into AND. `FeatureAll` is substituted with false and Boolean constants simplified: this removes LLVM's synthetic disassembler bypass, not an architectural alternative. The remaining `SubtargetFeature` records are exposed with their original command-line spelling, description, verbatim Arm label, and implication edges. Non-assembler predicates are retained separately by name; they are not interpreted as MC gates.

This avoids a handwritten opcode table and preserves LLVM dependencies without expanding every possible feature combination. The feature graph is an LLVM enabling graph: an implication from NEON to FP says LLVM enables FP when NEON is enabled. It is not an independent proof of Arm execution-state legality. Likewise a grouped `ArchFeatureName` is an upstream label on a feature switch; splitting it into per-instruction requirements would be speculation.

The result describes the returned opcode's assembler predicates. It does not characterize every possible interpretation of the same bits under every feature configuration. In particular, HINT aliases, system-register names, decoder callbacks, streaming/ZA state, privilege, and operand-dependent architectural restrictions are not fully expressible through this interface. Missing gates do not establish base-ISA validity. The API reports this scope explicitly and returns `known: false` for absent records. It never labels unknown requirements as a known empty set.

The build-generated metadata shipped in the npm package is immutable at runtime. Instruction and register identities and formatted aliases can change when LLVM is upgraded; persist the exported `llvmVersion` alongside analysis results. Tests cover base gates, FP/SIMD dependencies, grouped labels, the SVE-or-SME alternative, modern extension instructions, invalid encodings, and a real AArch64 soft-fail.

`scripts/prepare-mc.mjs` generates an adapted MC factory translation unit in the build directory. It checks the pinned upstream source hash before adaptation and leaves LLVM's decoding, instruction analysis, and standard printing implementations intact. It omits encoding/object-writing registration and the Apple printer choice. For the fixed `generic` CPU, it retains the complete generated feature table, generic CPU feature/tuning bits, and hardware-mode methods; scheduling pointers use LLVM's default empty model instead of AArch64 scheduling tables. No opcode predicates, feature implications, or `+all` behavior are changed. This adapter also requires review on LLVM upgrades.
